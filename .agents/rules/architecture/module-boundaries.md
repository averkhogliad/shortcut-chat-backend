# Границы модулей и владение данными

Обязательные инварианты.

- Сервисные модули `users`, `chats`, `messages`, `notifications`, `mail-sender` зависят только от `common`. Не добавляй compile-зависимости между сервисами и не импортируй классы одного сервиса в другой.
- `common-test` — только test-support. Подключай его как `test` dependency.
- Каждый сервис владеет собственной БД или схемой. Не обращайся к таблицам другого сервиса, не вводи общий datasource и не используй общую БД как способ интеграции.
- Не «шари» сущности, репозитории и миграции между сервисами.
- Основной канал асинхронного взаимодействия — Kafka.
- Единственный разрешённый синхронный вызов — `notifications -> chats` через HTTP `GET /members`. Новые синхронные связи добавляй только по отдельному решению.
- `users` и `chats` публикуют события через transactional outbox: запись события и изменение агрегата происходят в одной транзакции.
- `messages` осознанно публикует событие после commit без outbox. Доставка не гарантирована. Не добавляй туда outbox и не меняй эту гарантию в локальной задаче.
- Не заявляй гарантированную доставку для outbox без отдельного решения: текущий handler не ждёт подтверждения Kafka.
- `tx-outbox/` — задел на будущую библиотеку, а не модуль. Не создавай и не выделяй её в локальной задаче.
- Синхронизация read-моделей `users`/`chats` в другие сервисы — будущая задача. Не выдавай текущие несинхронизированные данные за источник истины.
