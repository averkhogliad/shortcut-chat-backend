# Контракты API и Kafka

Обязательные правила при изменении REST API, DTO, ответов, ошибок и Kafka-взаимодействия.

## REST API

- Не переименовывай и не удаляй существующие endpoint'ы, поля и параметры. Не меняй типы и HTTP-методы.
- Обратная совместимость — аддитивная: добавляй только необязательные поля и параметры.
- Создание сейчас возвращает `200`, а не `201`. Не меняй статус без явной задачи.
- Сохраняй контракт пагинации `SliceResponse { data, next }`, где `next` — id последнего элемента, а не признак наличия следующей страницы.
- Сохраняй текущий формат ошибок `ProblemDetail`.
- Не меняй семантику существующего поля. Для нового поведения добавляй новое поле или endpoint.

## Kafka

- Сохраняй топики и назначение событий: `MailerCommands`, `UserLifecycle`, `ChatLifecycle`.
- Сохраняй заголовки: `X-Event-Id`, `X-Event-Name`, `X-Event-Version`, `X-Published-At`, `X-Published-By`.
- `X-Event-Name` — дискриминатор типа у consumer'а `notifications`. Новый тип события требует согласованного изменения producer'а и consumer'а.
- Изменение payload — аддитивное. Для несовместимого изменения используй новое имя или версию события, не переиспользуй существующее имя с другой семантикой.
- Не унифицируй сериализацию без согласования: `users`/`chats` публикуют байты из outbox, `messages` — JSON с отключёнными type headers.
- Не ломай идемпотентность `mail-sender`: ключ — `X-Event-Id`, состояние хранится в Redis с TTL 30 дней.
- В проекте нет DLQ, retry, schema registry и Kafka-транзакций. Не описывай поведение как exactly-once и не добавляй эти механизмы без отдельной задачи.
- При изменении ключа, заголовков или формата события обновляй всех затронутых consumer'ов в той же задаче.
