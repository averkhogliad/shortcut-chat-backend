# Стиль тестов Kotlin

Стандарт для `*Test.kt` и генераторов данных. Выбор проверки и команды — `verification.md`;
требования отдельной функции — в задаче или спецификации.

## Хороший тест

Проверяет внешнее поведение через публичный шов и не зависит от деталей реализации: никаких
проверок приватных методов, никаких ассертов на внутреннее устройство сверх наблюдаемого публично
факта.

## Стек

Kotest, MockK/SpringMockK, JUnit Platform. Версии — POM, не выдумывай команды и зависимости.

Общий конфиг — `common-test/SpringAwareKotestConfig` (`SpringExtension`,
`SpringAutowireConstructorExtension`). В каждом тестовом модуле
`src/test/resources/kotest.properties` отключает сканирование classpath и задаёт FQN конфига.
Не включай сканирование и не дублируй конфиг внутри модуля.

## Структура spec

Класс теста наследует `FreeSpec`. Первый уровень вложенности — тестируемый метод, второй и глубже —
проверяемые кейсы этого метода. Один метод — один блок; кейсы не размазываются по классу. Имя кейса
описывает наблюдаемое поведение, а не вызов; внутри кейса — секции `// given`, `// when`, `// then`.

```kotlin
class MailSendServiceTest : FreeSpec({

    "send" - {
        "throws IllegalArgumentException if no receiver email" {
        }

        "creates MailMessage and pass to MailSender" {
        }
    }
})
```

Вложенность глубже двух уровней допустима, когда у метода есть осмысленные группы поведения.

## Данные генерируются, а не выдумываются

`Gen<T>` — тип параметра генератора, конкретные реализации — `Arb` (случайные значения) и
`Exhaustive` (перебор). Генераторы живут рядом с тестами в `src/test`, в `gen.kt` того же пакета.
Одиночные генераторы оформляются как расширения `Arb.Companion`:

```kotlin
fun Arb.Companion.userEntities(
    ids: Gen<UUID?> = Exhaustive.of(null),
): Arb<UserEntity> = Arb.bind(ids, Arb.string()) { id, name -> UserEntity(id, name) }
```

Когда параметров слишком много или группу полей надо переиспользовать, они собираются в держатель —
класс с полями `Gen<...>` и дефолтами, который генератор принимает одним параметром:

```kotlin
class MediaMetaGens(
    val ids: Gen<String> = Arb.string(1..8),
)

fun Arb.Companion.mediaMetas(fieldGens: MediaMetaGens = MediaMetaGens()): Arb<MediaMeta> =
    Arb.bind(fieldGens.ids) { id -> MediaMeta(id) }
```

Составные значения собираются через `Arb.bind(...)`, а не через `randomUUID()` и литералы. Прогон
генератора — `checkAll(gen) { ... }`, один сэмпл — `gen.next()`. Жёсткие литералы (`"subject"`, `42`)
оставлять только там, где значение проверяется как ожидаемое, а не как вход.

Общий код нескольких spec-классов модуля (сборка среды, её настройки, проверки каталога) живёт в
отдельном файле рядом с тестами в `src/test`; генераторы остаются в `gen.kt`. Сорсета
`src/testFixtures` в проекте нет — не заводи его без явной задачи.

## Моки: query-методы против command-методов

Роль метода важнее типа класса. Query-метод возвращает значение: заглуши вход и результат, проверь
результат, вызов не верифицируй. Command-метод меняет состояние: заглушка принимает любой аргумент,
затем `verify` с `capture`, и захваченный аргумент сверяется с ожидаемым значением, а не с тем же
моком.

```kotlin
// query: проверяется результат, не вызов
val actual = service.load(id)
actual shouldBe entity

// command: проверяется переданный аргумент
val slot = slot<SimpleMailMessage>()
verify { emailSender.send(capture(slot)) }
slot.captured shouldBeSameInstanceAs mailMessageForSender
```

Полное правило, включая признаки нарушения, — глобальное `mock-query-vs-command.md`.

## Очистка состояния — флоу-методами

Моки и прочее состояние чистятся в `afterTest`, `afterEach`, `beforeTest`, `beforeSpec`, а не
вручную в каждом кейсе:

```kotlin
class MailSendServiceTest : FreeSpec({
    afterTest { clearAllMocks() }
})
```

Ручная очистка внутри кейса — исключение, оправданное только когда тест проверяет поведение между
вызовами.

## Нет тестовых хуков в продакшене

В продакшн-коде не бывает методов, свойств и аксессоров, существующих только для тестов:
`internal`-геттеров внутренних коллекций, методов вида `activeTaskIds()`, полей с пометкой
`visibleForTesting`. Такой хук расширяет API навсегда, а тест через него проверяет реализацию.

Проверяй через публичный шов. Если у свойства нет наблюдаемого следствия, теста на него не пишут:
свойство либо закрыто конструкцией (порядок операций исключает дефект по построению), либо вынесено
в отдельную единицу со своим контрактом и тестируется через её шов. Тестовые двойники швов хуками
не являются.

## Скоупы и temp-каталог в afterSpec

Скоуп, пишущий в temp-каталог теста, переживает тест: реактивный `collect` не завершается, пока
скоуп жив, и `runTest` его не ждёт. Перед удалением каталога в `afterSpec` такие скоупы
останавливаются.

- Не привязывай не-завершающийся реактивный job к `runTest` — тест будет ждать вечно.
- Остановка — `cancel` + `join` с таймаутом: на test-dispatcher scheduler гаснет с концом теста,
  отменённые `finally` не отрабатывают, и `join` без таймаута зависает.
- Удаляй с повторами до таймаута и re-throw на исчерпании: на Windows открытый хэндл удалённого
  файла держит запись в delete-pending, и `deleteRecursively` роняет весь билд. Настоящий leftover
  обязан ронять, а не глушиться.
- Общий teardown — один источник истины.
